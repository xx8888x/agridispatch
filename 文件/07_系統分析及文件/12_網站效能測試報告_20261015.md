# 智農派工 (AgriDispatch) 網站整體性能測試報告

> 測試日期：2026-10-15。受測版本：git `a9e1fdb`（HEAD 已提交版本的快照，後端與前端 `demo/`、`web/` 兩份）。
> 範圍：後端 API（Spring Boot 單體）＋ 前端網頁（農場主、工作者、科技後台）。**依指示不含 LINE Bot 與 Android。**
> 驗證標示：✅ 已實測｜⚠️ 由讀程式碼推論（未另行分析器驗證）｜❌ 未做。本次**未修改任何產品程式碼**，只產出測試結果與建議。

## 一、結論摘要

**整體評價：後端容量對第一年規模（外展移工 12 人、本土兼職 12 人、農場主數十戶）綽綽有餘；真正會被使用者感受到的是「手機網路下首次載入太慢」，其次是少數 API 的 SQL 次數過多、隨資料量成長會變慢。** 全部測試共約 52 萬次 API 請求、約 400 次頁面載入，**後端 API 0 個非 2xx／連線錯誤**（頁面測試僅出現兩個與後端無關的小錯誤，見 4.6），沒有發現功能性錯誤。

重點發現（細節與證據見第五章）：

| # | 發現 | 證據 | 優先級 |
|---|---|---|---|
| 1 | 手機 4G 模擬下首次載入極慢：FCP 7.5～17 秒（web 7.5～9.6、demo 13～17）、頁面載入完成 12～26 秒 | 章節 4.3；每頁傳輸 1～2.4 MB 且**完全未壓縮** | **P1** |
| 2 | 開啟 gzip 後傳輸量降 56～76%、手機 FCP 提早約 2～3 秒（web 版）／8～12 秒（demo 版）（對照實驗） | 章節 4.3 | **P1（最便宜）** |
| 3 | Tailwind「Play CDN」在瀏覽器端即時編譯 CSS，是前端主執行緒最大成本：封鎖它後 FCP −59%、TBT −80% | 章節 4.4 | **P1** |
| 4 | **公開（免登入）的 `POST /api/orders/calculate` 一次 73 條 SQL，單人 77 ms，全機上限僅約 95 req/s**——試算只為了取「建議工班名稱」卻跑了完整媒合排序 | 章節 3.1、3.8 | **P1** |
| 5 | 媒合（103 SQL）與技能彙總（133 SQL）是 N+1 查詢，單次 120～150 ms，高並發下 p95 超過 1 秒 | 章節 3.3、3.8 | P2 |
| 6 | 建立訂單速度隨訂單數線性變慢（50 → 20 req/s），訂單清單無分頁（1,520 筆 = 1.6 MB／150～190 ms） | 章節 3.5 | P2 |
| 7 | 天候 API 在 `synchronized` 方法內做外部 HTTP：首次呼叫 3.9～4.8 秒（實測），快取過期時推論同樣發生、期間其餘請求排隊 | 章節 3.1；程式 `WeatherService.java:88` | P2 |
| 8 | 登入每次約 2 秒（PBKDF2 31 萬次）且「帳號不存在」也算一次完整雜湊；成功登入沒有全域併發限制 | 章節 3.4 | P2（小主機上風險更大） |
| 9 | 靜態資源無長期快取、前端有 1.8 MB 未引用的開發版 Vue、`lucide` 整包圖示 432 KB、Google Fonts 外部相依 | 章節 4.5 | P3 |
| 10 | 3 個頁面 CLS 超過 0.1（版面位移）；demo 科技後台直連 open-meteo 被限流（HTTP 429） | 章節 4.6 | P3 |

**一句話建議**：先做 #2（Nginx／Spring 開 gzip，數行設定）與 #4（試算不跑完整媒合），兩者成本最低、效益最大；#3 為中等工作量但對手機體驗最有感。

### 2.4 限制（請在解讀數字時一併考量）

- 頁面指標中的 **TBT 以瀏覽器 `longtask` 觀察值（超過 50 ms 的部分）累計**，與 Lighthouse 的定義略有差異，適合做版本間的相對比較。
- **負載產生器與受測服務同機**，且測試期間整機 CPU 平均 94.5%（另有 Unity、另一個工作階段的 JVM 等程式在跑），所以**吞吐量數字偏保守**，專用主機上會更高；但「哪些端點相對很慢」的排序與 SQL 次數不受影響。
- 本機是 **H2**，DEV／正式環境是 **Oracle**：N+1 查詢在 Oracle（每條 SQL 多一次網路往返）上只會更慢，影響比本報告的數字更大 ⚠️。
- 手機數字是 Chrome DevTools 的節流模擬，不是真實手機；真實低階 Android 可能更慢。
- **DEV 主機（Oracle Cloud 大阪）未測**——對共用測試環境施壓需要你同意（見第六章）。
- 已排除：LINE Bot（port 5000）、Android App，以及頁面 `linebot/line.html`、`line-bind.html`、`admin-line.html`、外勞頁與黑轉白頁（功能開關目前下架）、`coldchain.html`／`app.html`／`verify.html`。

登入洪泛（12 並發連續登入）期間，其它 API（`GET /api/orders`，10 並發）p50 5.4 → 4.3 ms、p95 12.1 → 10.4 ms。

- 單次登入約 **2.0～2.1 秒**（本機且整機 CPU 忙碌時實測）；**帳號不存在也要 2.5 秒**（表示後端對不存在的帳號也做完整雜湊，這是防止「以回應時間探測帳號是否存在」的好設計，但代價是每次嘗試都燒 1 核 CPU 約 2 秒）。
- 登入並發 12 以上時登入本身排隊（12 並發 p50 3.7 秒、48 並發 11.8 秒），但這 12 核機器上其它 API 沒被拖慢（p50 5.4 → 4.3 ms）。**在 DEV／正式規劃的雲端主機（核心數遠少於本機的 12 執行緒）上，登入洪泛就可能影響其它請求** ⚠️。
- PBKDF2 31 萬次符合 OWASP 現行建議，**不建議降低次數**；建議改用全域併發上限／限流（見 5.7）。

## 五、問題清單與優化建議

> 每項包含：現象／根因（程式位置）／建議／預期效益／如何驗證。「預期效益」中標 ⚠️ 的是推估，優化後請重跑 `Software/tools/perf/` 內的腳本確認。

### 5.1 P1：啟用 gzip／brotli 壓縮

- **現象**：API 與靜態檔都沒有 `Content-Encoding`；每頁傳輸 1～2.4 MB（✅）。
- **根因**：`application.yml` 未設 `server.compression`；`WebConfig.java:54-76` 的靜態資源處理器只送原檔；`server-setup.sh` 的 Nginx 設定沒有 `gzip`。
- **建議**（二選一，建議放在 Nginx）：
  - Nginx：`gzip on; gzip_types text/css application/javascript application/json text/html image/svg+xml; gzip_min_length 1024;`（可再加 brotli 模組）。
  - Spring Boot：`server.compression.enabled=true`、`server.compression.mime-types=application/json,text/html,text/css,application/javascript,text/javascript`。
- **預期效益**：傳輸量 −56～76%、手機 FCP 提早 2～3 秒（web）／8～12 秒（demo）（✅ 對照實驗）；天候 API 207 KB → 15 KB（✅ 實測 gzip 後大小）；訂單清單 17 KB → 4 KB。
- **驗證**：`curl -s -D - -o /dev/null -H "Accept-Encoding: gzip" https://<DEV>/web/AgriDispatch/js/vendor/vue.global.prod.js`，應看到 `Content-Encoding: gzip`。

### 5.2 P1：Tailwind 改為預先編譯的靜態 CSS

- **現象**：每頁載入 398 KB 的 Play CDN 並在瀏覽器即時編譯（✅ 封鎖實驗：FCP −59%、TBT −80%）。
- **建議**：用 Tailwind CLI（獨立執行檔即可，不需要 npm 專案）依 `content` 掃描 `demo/**/*.html`、`demo/**/js/*.js` 產生一支 `agri.tailwind.css`，頁面改引用它；`tailwind.config` 的共用設定目前在 `js/agri-theme.js`（部分頁面另有內聯設定），改放獨立的 `tailwind.config.js`。產出的 CSS 通常 < 50 KB（gzip 後約 10 KB）。
- **注意**：動態拼出來的 class（例如 JS 字串組出的顏色）要加進 `safelist`，否則會缺樣式；改完需逐頁目視確認，這也是工作量主要來源。
- **預期效益**：手機首次繪製再縮短約一半、TBT −80%（✅ 封鎖實驗為上限估計）。

### 5.3 P1：公開試算端點不要跑完整媒合

- **現象**：`POST /api/orders/calculate` **免登入**、單次 **73 條 SQL**、單人 77 ms、全機上限約 95 req/s；它是免登入可呼叫的 CPU 放大端點（✅）。
- **根因**：`OrderService.java:283` 的 `matchingProvider.getObject().suggestTeamId(draft)` 為了取「建議工班名稱」，呼叫 `MatchingService` 的完整排序（每個工班各查成員、保險、評價、技能、負載，`MatchingService.java:144-170`）。
- **建議**（由簡到繁）：
  1. 對 `(派工類別, 人數, 時段)` 的建議工班結果做 30～60 秒的記憶體快取（工班排序不會每秒變）；
  2. 試算改為「先算金額，建議工班延後到真正下單／進入媒合頁才算」；
  3. 對該端點加 IP 限流（它不需要登入）。
- **預期效益**：單次延遲預期由 77 ms 降到個位數毫秒、吞吐量提升一個數量級 ⚠️。
- **驗證**：重跑 `run_load.mjs`，看 A 組 `POST /api/orders/calculate` 與 B 組混合流量。

### 5.4 P2：媒合與技能彙總的 N+1 查詢

- **現象**：`GET /api/matching/orders/{id}` 103 條 SQL、`GET /api/skills/workers` 133 條 SQL（✅）。
- **根因**：`SkillService.java:93-100`／`:161` 對每位工人各自查出勤、評核、保險、評價（`profile(w, today)` 迴圈內呼叫 repository）；`MatchingService.java:149-170` 對每個工班各自查成員與負載。
- **建議**：一次以 `IN (...)` 批次載入所有工人的出勤／評核／保險／訂單，再於記憶體組裝（Spring Data `findByWorkerIdIn` 已有範例，`MatchingService.java:151`）；技能彙總結果可加 1～5 分鐘快取。
- **預期效益**：SQL 由 100+ 條降到約 5～10 條，延遲預期降一個數量級，**在 Oracle 上效益更大** ⚠️。

### 5.5 P2：訂單寫入隨資料量變慢、清單無分頁

- **現象**：建立訂單 50 → 19.6 req/s（16 → 1,500 筆）；`GET /api/orders` 1,520 筆 = 1.6 MB（✅）。
- **根因**：
  - `OrderService.java:508-510`：全域 `synchronized (idLock)` 內用 `findIdsByPrefix` **撈出全部 ID** 再挑下一號（O(n)，且所有寫入序列化）；
  - `OrderService.java:501`：每次建立訂單都跑一次完整媒合排序，其中 `MatchingService.busyWorkers` 會 `orderRepository.findAll()`（`MatchingService.java:332`）；
  - `OrderService.java:83-85`：`getAllOrders()` 回傳全部訂單，沒有分頁。
- **建議**：訂單編號改用資料庫序列（Oracle SEQUENCE／H2 sequence）；撞期檢查改成以日期區間下推 SQL 條件；清單 API 加 `page/size` 與狀態、日期篩選，前端預設只取近期。
- **預期效益**：寫入速度不再隨筆數惡化；清單回應固定在幾十 KB ⚠️。

### 5.6 P2：天候 API 在鎖內做外部呼叫

- **現象**：首次呼叫 3.9～4.8 秒（✅ 兩次實測）；快取（30 分鐘）過期時，推論第一位使用者同樣要等約 4～5 秒 ⚠️。
- **根因**：`WeatherService.java:88` 的 `getTowns` 是 `synchronized`，且在鎖內呼叫 `fetchAll`（約 12 個外部 HTTP 請求），期間**所有天候請求都被擋在鎖外排隊**。
- **建議**：改為背景排程預熱（`@Scheduled`）＋「過期仍先回傳舊資料、背景更新」（stale-while-revalidate）；外部呼叫放在鎖外。
- **預期效益**：使用者永遠讀到快取（~10 ms），不再有 5 秒尖峰 ⚠️。

### 5.7 P2：登入保護

- **現象**：單次約 2 秒；帳號不存在也約 2.5 秒；高並發登入時排隊（✅）。
- **建議**：保留 31 萬次（不降低）；在 `/api/auth/login` 加**全域併發上限**（例如同時最多 CPU 核數的一半個雜湊在跑，其餘排隊或回 429），避免登入洪泛耗盡小主機 CPU；`LoginRateLimiter` 已限制失敗次數，但成功登入與多 IP 來源不受限。
- **預期效益**：登入洪泛時其它 API 不受影響 ⚠️。

### 5.8 P3：前端資源瘦身與快取

- 對 `js/vendor/**`（檔名已含版本或內容固定）設 `Cache-Control: public, max-age=86400`（或更長），其餘維持 `no-cache` 條件式請求；目前 DEV Nginx 一律覆寫為 `no-cache`（`server-setup.sh:233-236`）。
- 刪除 3 份未引用的 `vue.global.js`（共 1.8 MB，`web/`、Android `assets/www/` 也會一併同步進去）。
- `lucide.min.js`（432 KB）改為只內嵌實際使用的圖示（SVG sprite 或自建精簡版）。
- `demo-fixtures.js`（818 KB）改為按頁面／按需載入（目前以 `document.write` 同步載入，阻擋解析）。
- Google Fonts：加 `preconnect`、`font-display: swap`，或自架 Noto Sans TC 子集。
- 腳本加 `defer`（需注意 `document.write` 的載入順序，這是改動風險最高的一項）。

### 5.9 P3：CLS 與 demo 天候直連

- 在 `worker-skills`、`admin`、`payroll` 的非同步內容區預留高度（`min-height`／骨架畫面）。
- `demo/TechBackend/admin.html` 的 open-meteo 呼叫改走後端或 Mock 預錄資料，避免路演現場被 429；`favicon.ico` 補一個。
